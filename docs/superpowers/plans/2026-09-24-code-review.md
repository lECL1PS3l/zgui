# План ревью кода Z GUI (для агента-ревьюера)

> Задача агента: провести техническое ревью репозитория `E:\Base\opencode\Z GUI` и выдать находки. Только чтение: код НЕ менять, тесты НЕ править. Правки — отдельной задачей после ревью.

**Цель:** найти дефекты, из-за которых пользователь потеряет функциональность, настройки или получит зависание/повышение привилегий; подтвердить или закрыть каждый открытый пункт из `Context/Context.md` → «Фикс лист».

**Область:** `src-tauri/src/*.rs` (бекенд, ~10 800 строк) + `src/main.js` (2 589) + `index.html` (489) + `src/styles.css` (897). Сборка/CI, скрипты релиза — по остаточному принципу.

**Стек:** Rust (Tauri 2), PS 5.1 для привилегированных операций, WinDivert-движки, vanilla JS фронт.

**Спека/контекст:** `Context/Context.md` (профиль, фикс-лист, история), `docs/superpowers/specs/2026-09-23-multiengine-design.md`.

## Как запускать проверки

Всё — из корня репо, PowerShell 5.1:

```powershell
cargo check --manifest-path src-tauri/Cargo.toml            # ожидается 0 warnings
cargo test --manifest-path src-tauri/Cargo.toml --lib       # ожидается 66 passed
cargo test --manifest-path src-tauri/Cargo.toml --lib -- --test-threads=1   # если падают logger::tests — это флаки
node --check src/main.js                                    # синтаксис фронта
npm run build                                               # сборка фронта (vite)
```

Проверка кодировки (обязательна после любых правок .rs/.js):

```powershell
# BOM у .rs/.js — дефект; у .ps1 — норма
[System.IO.File]::ReadAllBytes("src-tauri/src/lib.rs")[0..2]
# двойная перекодировка кириллицы: маркеры U+0402..U+040F/U+0452..U+045F
```

## Правила и ловушки (соблюдать при ревью)

1. **НЕ править `.rs`/`.js` через `Get-Content | Set-Content`** — PowerShell 5.1 читает UTF-8 без BOM как CP1251 и портит кириллицу (в проекте уже был такой инцидент). Ревьюер и так ничего не меняет.
2. **Консоль CP866 искажает вывод.** «Краказябры» в терминале — не признак битого файла. Проверять содержимое через `[System.IO.File]::ReadAllText($p, [Text.Encoding]::UTF8)` или инструментом чтения.
3. **`cargo build --release` НЕ пересобирает `dist/`** (фронт). Нужен `npm run build` или `npx tauri build`. Для ревью это важно: расхождение dist и src — дефект сборки.
4. **exe занят при запущенном приложении** (os error 5) — сборку не запускать, если `Get-Process zgui` не пуст.
5. **Логгер-тесты флаки** при параллельном прогоне (общий глобальный буфер). Не считать их падение дефектом без однопоточного подтверждения.
6. **Публикацию/пуш не делать** — только по команде владельца.
7. **Среды:** локальная машина — Windows 11 x64, путь установки содержит пробел (`E:\Base\opencode\Z GUI`) — это важный тест-кейс, а не аномалия.

## Кросс-проектные инварианты (проверять целенаправленно)

1. **Порядок блокировок.** Фиксирован: `OPS` (мьютекс операций) → `testing` → `state`. Любое место, берущее `state` до `testing` (или наоборот), — потенциальный дедлок. Найти все захваты `g.testing` и `st(g)` и проверить вложенность.
2. **Одна операция за раз.** Каждая долгая операция обязана брать `ops_try()` и снимать `op_running` во ВСЕХ ветках (включая фоновые потоки и ранние `return Err`).
3. **Персистентность.** `AppState` round-trip: `roots` (плоский map + легаси `{"flowseal":...}` + формат 1.3.0 `{"map":{...}}`), `settings` (серверные поля `theme/boot_app/tg_secret/tg_offer/admin_onboarded` не должны теряться при сохранении формы).
4. **Пути с пробелами.** Установка в `...\Z GUI\...`: аргументы движков, пути Lua (`@file`), `--blob=name:@file`, UAC-лаунчер, командная строка службы — везде корректный квотинг. Отдельно: `.bat`-токенизатор (`profiles.rs`) с пробелами и `^`-продолжениями.
5. **Не доверять вводу извне.** Имена процессов (из `tasklist`) попадают в админские PS-скрипты — обязательна защита от инъекции (массивы/экранирование). Проверить `service.rs::kill_conflicts`, `netreset.rs`, `dns.rs`.
6. **Тест-раннер.** Маркеры `logs/test-*.pid|flag|json`: корректность «жив/умер», отсутствие вечного «тест выполняется», отсутствие авто-подхвата чужого/старого раннера, гашение при выходе.
7. **Реестр движков — единый источник правды.** Никаких остаточных `if engine == ENGINE_FLOWSEAL` в путях запуска/службы/тестов; `exe_name` только через `EngineDef`.
8. **Фронт ↔ бекенд.** Каждый `invoke("<cmd>")` должен существовать в `invoke_handler`; каждый `$("#id")` — существовать в `index.html`; поля `Bootstrap` — совпадать по именам (camelCase!). Известный класс: `tg_port` vs `tgPort`.

## План ревью по полосам (lanes)

### Полоса 1. Привилегии и выполнение процессов (`runner.rs`, `service.rs`, `netreset.rs`, `dns.rs`)
- `run_script_privileged`: корректность ветки «уже админ» vs UAC; проброс кода выхода; утечки временных `.ps1`.
- Инъекции: все PS-скрипты, куда попадают внешние строки (имена процессов, имена служб, пути). Аргументы через `-Command` vs отдельные `-File`/`-ArgumentList`.
- `kill_conflicts`: реально ли убивает (PID+имя), остановка/disable служб по PathName, повторные попытки, идемпотентность, что с protected-процессами (нужен ли фоллбэк).
- `build_service_cmdline`: квотинг при пробелах; `New-Service -BinaryPathName`; запись `zgui-strategy`; удаление/остановка старой службы.
- `netreset`: не выполняет ли что-то, рвущее сеть, без явного согласия пользователя; `route -f`/`release` вне кнопки.
- **Доказательство:** чтение кода + (если возможно) генерация `.ps1` в temp и визуальная проверка квотинга.

### Полоса 2. Персистентность и конфиг (`config.rs`, `lib.rs::set_settings`, `provision_*`)
- `Roots` Serialize/Deserialize: все три формата читаются; round-trip не теряет данные; битый `state.json` → бэкап `.bad-<ts>`.
- `set_settings`: полная замена `Settings` не должна стирать серверные поля (см. инвариант 3). Проверить каждое поле, которое фронт не шлёт.
- Миграции: `interval_migrated`, вырезанные движки/пресеты, чистка `presets::REMOVED_PRESET_IDS`, сброс `autostart_profile` на удалённый профиль.
- `ensure_presets` не должен удалять OTA-пресеты (id которых нет во вшитой таблице).
- **Доказательство:** `cargo test`, плюс скриптовый round-trip `serde_json` в `cargo test`-манере (можно временным тестом в scratch, но не коммитить).

### Полоса 3. Реестр движков и дистрибуция (`config.rs::engines`, `presets.rs`, `embedded.rs`, `lib.rs::*engine*`)
- Все места «какой движок» идут через `EngineDef`/`engine_def`; нет хардкода `winws.exe`.
- `set_root`/`fetch_engine`/`fetch_engine_impl`: поиск exe/ассета, self-репо для zapret2, устойчивость к отсутствию zip/иному имени ассета.
- `embedded::extract_all`/`ensure_engine`: защита от zip-slip, срезка верхнего каталога, атомарная запись.
- `presets::prepare_args`: `%ENGINE_ROOT%`/`%GameFilterTCP|UDP%`, нормализация слэшей, аргументы без плейсхолдера не трогаются; `--blob=name:@file` и `--wf-raw-part=@file` корректны для winws2.
- **Доказательство:** `cargo test`, `scripts/fetch-engines.ps1` (читая), ручная сверка пресетов с `preset2_example.cmd` (bol-van/zapret-win-bundle).

### Полоса 4. Тестер, кэш и автоподбор (`tester.rs`, `autotune.rs`, `lib.rs::test_*`, `lib.rs::autotune_*`)
- Генерация PS-раннера: ASCII-only, квотинг args (пробелы, `@`, кавычки), путь `run-*.err.txt`, повтор при мгновенном падении, «второй шанс».
- `test_status`/`cancel_test`/гард `test_strategies`: фантомы, гонки, «тест уже выполняется», гашение при выходе/старте.
- Скоринг `summarize`: критерий лучшей (`started && critical_ok`), сравнение по score/avg_ms, отсутствие паник на пустом наборе.
- Мост переиспользования: `args_key` (engine+tcp/udp+args), окно 1 ч, только `started`, слияние `reused`+`parsed`, корректность `done`, пустой `steps`.
- `autotune::candidates`: уникальность, валидность аргументов под движок (сверить с докой движков), отсутствие «мусорных» id.
- **Доказательство:** `cargo test`, чтение артефактов `data/logs/test-runner.ps1`/`test-out.json` (если есть), `winws2.exe --dry-run` со сгенерированными args (если движок на месте).

### Полоса 5. Обновления и OTA-пресеты (`updater.rs`, `lib.rs::check_updates/apply_updates`)
- `collect_entries`: whitelist, `catalog_only`, `ipset_mode`.
- `check_entry`/`check_all`: статусы, устойчивость к сбоям сети, отсутствие «залипания» групп, лишние round-trip/латентность.
- `apply_updates`: backup → atomic_write → `archive.record`; независимая обработка файловой части и набора пресетов (при `Err` файлов часть пресетов не должна теряться); «пустой ids == все» не должно срабатывать при выборе только набора.
- `parse_preset_set`/`apply_preset_set`: только `builtin` c `preset:<id>`; кастомные не трогаются; нестроковые args отвергаются.
- **Доказательство:** `cargo test`, чтение `release/presets.json`, `presets.rs::preset_set_json` round-trip.

### Полоса 6. Telegram и системные интеграции (`telegram.rs`, `lib.rs::tg_*`, `watchdog.rs`)
- `TgState::start/stop/status`: потоки, порт, `--secret`, отсутствие дедлоков (`save()` не под state-локом), корректный стоп.
- `tg_offer`/`tg_offer_reset`: раз за сессию, троттл, условия (Telegram запущен, VPN пуст, не `tg_autostart`, мост не активен).
- `telegram_running`/`detect_vpn`: корректность разбора `tasklist` CSV, отсутствие ложных срабатываний (Radmin-адаптер ≠ VPN-процесс).
- `tg_vpn_guard`: троттл, гашение моста, отсутствие циклов.
- **Доказательство:** чтение кода, сверка условия с требованиями из контекста.

### Полоса 7. Фронт (`src/main.js`, `index.html`, `styles.css`)
- Сводка id: каждый `$("#...")` есть в HTML (автоматизировать grep-ом и сверить списки).
- Сводка команд: каждый `invoke("...")` есть в `invoke_handler` (сверить списки).
- Имена полей `Bootstrap`/`Settings` (camelCase, `tg_port` и т.п.).
- Состояние UI: табы движков (профили/тесты/автоподбор), «Выбрать все» (визуальная синхронизация чекбоксов), фильтр «Автоподбор», геоблок у края, плитки обновлений.
- Обработчики: нет ли повторной привязки при перерисовке (утечки), нет ли «мёртвых» id, нет ли исключений в рендерах при `B === null`.
- **Доказательство:** `node --check`; при возможности — прогон фронта в браузере с mock `__TAURI_INTERNALS__` (bootstrap с 4 движками) и ручная проверка DOM (без обязательных скриншотов).

## Review Focus (классы входа, которые чаще всего «кусают» пользователя)

Проверить каждый — есть ли тест или явная обработка; если нет, это находка:

1. **Путь установки с пробелом** (`...\Z GUI\...`) — запуск профиля, служба, тест, Lua `@file`.
2. **Битый/чужой/старый `state.json`** (в т.ч. формат `{"map":{...}}` и легаси) — не потерять настройки, сделать бэкап.
3. **Профиль/пресет ссылается на незарегистрированный или неустановленный движок** — внятная ошибка, не паника, не «молча ничего».
4. **Устаревший тест-раннер после жёсткого закрытия** — не подхватывается, гасится, не блокирует новые прогоны.
5. **Отказ UAC** на любой привилегированной операции — понятное сообщение, отсутствие «вечного» повтора и зависания.
6. **Одновременные операции** (тест + запуск профиля + обновления + netreset) — взаимная блокировка без дедлоков и без параллельных winws.
7. **Гигантские/пустые списки доменов и `.bat` в UTF-16** — без паник, без потери стратегий.
8. **Аргументы кандидата автоподбора с кавычками/`@`/пробелами** — корректный проброс в процесс.

## Рубрика серьёзности

- **Critical** — потеря данных/настроек, повышение привилегий, невозможность запустить/остановить обход, зависание UI, регресс, ломающий основную функцию.
- **Important** — функция работает неверно в реалистичном сценарии, но есть обходной путь; потеря результата теста/обновления; некорректная ошибка, вводящая в заблуждение.
- **Minor** — стиль, латентность, дублирование, мёртвый код, отсутствие теста на некритичный путь.

## Формат отчёта

По каждой находке:
```
[Severity] file:line — что не так (одна фраза)
Причина: почему это дефект (механика).
Сценарий: как пользователь это получит (шаги).
Доказательство: команда/чтение/наблюдение.
Правка: минимально достаточная (без реализации, только направление).
```
Затем:
- **Проверено и корректно** — список проверенных инвариантов (чтобы не перепроверяли заново).
- **Не проверено** — что не удалось (с причиной).
- **Открытые пункты фикс-листа** — по каждому: подтверждён / закрыт / переклассифицирован.

## Открытые пункты фикс-листа (подтвердить или закрыть)

Взять актуальный список из `Context/Context.md` → «Фикс лист». На момент постановки открыты:
- `zapret2` даёт низкий счёт (0–49/115) — принять как наблюдение, не дефект кода без доказательств.
- `DPIBreak` почти все режимы 0/115.
- В релизном `engine-zapret2.zip` нет новых файлов бандла — задача публикации, не ревью.
- Отложенные миноры: лишний round-trip за пресетами; `is_elevated()` без кэша; `gen_tg_secret` не crypto-RNG; `showConfirm` с одним `cmResolve`; изоляция флаки-тестов логгера.

## Вне области ревью

- Проверка реального обхода DPI на сети (нужен живой трафик/движки).
- UAC-взаимодействие вживую, WinDivert-перехват.
- Публикация релизов/пуш (только по команде владельца).
- Стилистика кода без влияния на поведение (в Minor, не более).
