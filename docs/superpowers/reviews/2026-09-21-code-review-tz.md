## 1. Что это за проект

- **Продукт**: портативная GUI-оболочка для Windows к движку
  [Flowseal/zapret-discord-youtube](https://github.com/Flowseal/zapret-discord-youtube)
  (`winws.exe`). Обход DPI-блокировок: запуск/остановка стратегий, тест стратегий,
  автообновление конфигов и движка, защищённый DNS, Telegram MTProto-прокси.
- **Репозиторий**: `E:\Base\opencode\Z GUI` (public GitHub `lECL1PS3l/zgui`,
  CI-пайплайнов нет, теги не проставлены, рабочее дерево не закоммичено).
- **Стек**: Rust (Tauri v2) + web-фронтенд на чистом JS (Vite, без фреймворка).
  Вся бизнес-логика в Rust, фронт тонкий (вызовы `invoke(...)`).
- **Платформа**: только Windows 10/11. Требует прав администратора для запуска
  обхода (winws поднимает драйвер WinDivert). Есть режим «всегда от администратора»
  и самоперезапуск с UAC.
- **Данные**: портативно, папка `data/` рядом с exe создаётся при первом запуске
  (движок и стартовые конфиги распакованы из ресурсов exe). Состояние —
  `data/state.json` (структура `AppState` в `src-tauri/src/config.rs`).
- **Движки**: остался один — Flowseal (winws). Движок zapret2/winws2 вырезан
  (миграция `migrate_removed_engine`).

### Как работает обход (доменная модель)

- **Стратегия (профиль)** — набор аргументов `winws.exe` (плюс `.bat`-пресеты
  Flowseal). Профили лежат в `AppState.profiles`.
- Обход можно поднять двумя механизмами, **взаимоисключающими**:
  1. **Программа**: GUI запускает `winws.exe` как дочерний процесс (`do_start`),
     запись о нём — `AppState.runtime`.
  2. **Служба `zapret`**: headless-служба Windows запускает winws без GUI
     (`service.rs`, установка создаёт Windows-службу, стратегия — в реестре).
- **Автозапуск**: либо задача планировщика `ZapretGUI` (`zgui.exe --boot` при
  входе, задача с уровнем «наивысшие»), либо служба. Не оба.
- **Тест стратегий**: по очереди поднимает winws каждым профилем (через
  PowerShell-раннер), проверяет контрольные домены HTTPS-пробой, выбирает лучшую.
  На время теста обход ему полностью принадлежит.

### 4.1. Суть переработки (что ревьюить в первую очередь)

Дизайн: `docs/superpowers/specs/2026-09-21-unified-run-state-design.md`.
Пользовательские жалобы, которые чинились:
1. После «сделать автостартом» стратегию нельзя запустить «прямо сейчас», пока не
   снимешь автозапуск/службу;
2. Программа ругалась на собственный winws как «внешний»;
3. Во время теста показывалось «zapret запущен не от нашей программы».

Ключевые сущности/функции в `lib.rs`:

- `WinwsOwner { None | App(profileId) | Service(Option<profileId>) | Test | External }`
  и чистая `winws_owner_of(testing, app_profile, service_running, service_strategy,
  any_winws, own_winws)`; `current_owner(&Global)` собирает факты; `owner_name()`.
  Приоритет: **тест → программа → служба → внешний → пусто**.
  Паблик-контракт: поле `owner: String` (`none|app|service|test|external`) в
  `Bootstrap` (команда `bootstrap`) — фронт рисует тулбар по нему.
- `start_or_switch(app, g, id)`: если служба установлена — пересоздаёт её под
  профиль (`svc::install_service`, идемпотентен) и стартует; иначе `do_start`
  (winws как процесс GUI). Блокирует запуск во время теста (`runner_alive`).
- `apply_best_strategy(app, id)` (заменил `set_best_strategy`): пишет профиль
  автозапуска + `TestCache.best_id` и **сразу запускает** через `start_or_switch`.
- `autostart_plan(service_installed, have_profile)` + `sync_autostart(g)`:
  единственная точка приведения механизма автозапуска к одному. Инвариант:
  **задача планировщика существует ⇔ нет службы И выбран существующий профиль
  автозапуска**. Вызывается из `set_settings`, `install_service`,
  `remove_service`, `apply_best_strategy`.
- `install_service`/`remove_service`: без «тупиковых» ошибок взаимной блокировки;
  удаление службы сохраняет профиль автозапуска (переход на программу).
- Команда `set_boot_app` **удалена** (её роль у `sync_autostart`) — проверь, что
  нет висячих ссылок во фронте и списке `generate_handler!`.
- `tester::runner_alive(data)` — маркер живого фонового раннера теста.

## 5. Архитектурные факты и правила (чтобы не напутать)

1. **Порядок блокировок**: `Global.testing` → `AppState` (state). Захватывать
   `testing`, уже удерживая `state`, **нельзя** — `test_status` делает
   `testing → state` вложенно; обратный порядок даёт дедлок.
   `current_owner()` берёт `testing`, отпускает, затем `state` — не вызывать её,
   удерживая `state` (это прямо задокументировано в коде). Проверь все новые
   вызовы `current_owner`/`st()` на вложенность.
2. **Семантика `service_running: Option<bool>`**: `None` — служба не установлена;
   `Some(false)` — установлена, но остановлена; `Some(true)` — запущена.
   «Установлена» = `is_some()`. Факт состояния освежается `svc::service_state()`
   в watcher раз в 10 с — возможна кратковременная устарелость.
3. **Watcher** (`spawn_watchers`, цикл 2 с): снимает `runtime`, если процесс умер;
   раз в 10 с обновляет состояние службы; считает `external_winws` через
   `current_owner()`. Важно: `external` не должен быть `true` для службы и теста.
4. **Автозапуск**: `provision_boot` при старте только «досоздаёт» задачу, если
   `boot_app == true` и её нет (и только под админом); `ack_boot` подхватывает
   событие `--boot` и стартует профиль, но **пропускает** запуск, если установлена
   служба.
5. **UAC**: создание/удаление задачи планировщика и службы может требовать
   повышения — `rn::apply_boot_task` бросает ошибку, если факт не совпал с
   ожиданием. `sync_autostart` — best-effort (ошибку пишет в журнал, не бросает).
6. **Фронт-контракт**: имена команд в `invoke` должны совпадать с
   `generate_handler!`; поля — camelCase (`serde(rename_all = "camelCase")`).
   Тулбар: `B.owner`, `B.runtime`, `B.service.{installed,running,strategy}`,
   `B.external`. Кнопка «Остановить» должна быть выключена, когда `owner == "test"`.

## 6. Чеклист ревью (что проверить; отмечай подтверждённое/нет)

Функциональная корректность новой модели:
- [ ] Инвариант единственного владельца winws: ни один путь (`start_or_switch`,
  `do_start`, `stop_all_own`, `install_service`, `remove_service`, старт/рестор
  теста, watcher, `ack_boot`) не оставляет **два** winws (программа + служба +
  внешний) одновременно.
- [ ] Автозапуск: все места, меняющие `autostart_mode`/`autostart_profile`/
  `boot_app` (включая `migrate_removed_engine`, `set_settings`, миграции), покрыты
  `sync_autostart` — задача либо есть, либо нет строго по правилу.
- [ ] `start_or_switch` при службе: корректный repoint (стратегия, состояние,
  отсутствие «тупиков»); при отсутствии службы — прямой запуск.
- [ ] `apply_best_strategy`: идемпотентность, порядок «сначала согласовать
  автозапуск, потом запустить», корректные ошибки.
- [ ] `remove_service`: сохранение автозапуска (переход на программу), корректные
  тосты/состояние, отсутствие осиротевших процессов.
- [ ] `owner` в `Bootstrap`: значения и приоритет совпадают с `winws_owner_of`;
  корректность при `service_running = Some(false)` и при мёртвом `runtime`.
- [ ] Тест: во время теста нет ложного `external`, запуск/остановка из UI не
  мешают тесту, после теста обход восстанавливается.

Конкурентность/надёжность:
- [ ] Порядок блокировок (см. п.5.1); нет вызовов `current_owner` под `state`.
- [ ] `sync_autostart` может блокироваться на UAC в асинхронном контексте —
  оцени влияние (команды `#[tauri::command(async)]`/`spawn_blocking`).
- [ ] Гонки в watcher: короткоживущие состояния, двойные emit, лишние `save()`.
- [ ] Обработка ошибок UAC/службы: частичные состояния, отсутствие паник,
  информативность (`human::with_context`).

Безопасность:
- [ ] Экранирование путей/аргументов в генерируемых `.ps1` (`ps_quote`,
  `write_utf8_bom`), отсутствие инъекций.
- [ ] Повышение прав только там, где нужно; не логируются секреты.
- [ ] `svc::detect_conflicts`/`kill_conflicts` не убивают свои процессы.

## 7. Известные осознанные компромиссы (НЕ считать багами)

Это решения владельца/автора, они допустимы (можно упомянуть как «принято», но не
как дефект):
- `start_or_switch` при службе возвращает `Runtime { pid: 0, via: "service" }`, но
  **не сохраняет** его в состоянии (владелец — служба). `pid 0` нигде не
  используется как реальный.
- В редких переходах возможно **два UAC-запроса** (например, `apply_best_strategy`
  при установленной службе и оставшейся задаче; `remove_service` с созданием
  задачи). Приемлемо.
- `sync_autostart` в общем случае срабатывает редко (ранний выход, если
  желаемое совпадает с текущим); блокировка на UAC — только в момент реального
  изменения.
- Внешний winws, оставшийся от старых версий, глушится `stop_all_own`. Задача
  планировщика, которую не удалось снять без прав, обезвреживается проверкой
  службы в `ack_boot` (двойного запуска не будет).
- `provision_boot` под не-админом молча пишет warning в журнал (задача не
  создаётся) — так задумано.
- `service_running` может быть устаревшим до 10 с (watcher-цикл) — допустимо.
- Автозапуск через задачу планировщика открывает GUI при входе — так задумано.
