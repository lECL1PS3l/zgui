## 2. Находки

### [Major] src/main.js:1802-1805 — «— не запускать —» при установленной службе не выключает автозапуск

**Проблема.** В обработчике `change` селекта `#cfAutostart`, если служба
установлена и выбран пункт «— не запускать —» (`val` пуст), вызывается только
`remove_service`, после чего показывается тост «автозапуск выключен».

**Почему.** `remove_service` на бэкенде (src-tauri/src/lib.rs:1846-1861) намеренно
сохраняет профиль автозапуска: если `autostart_mode == "profile"`, профиль
остаётся, и `sync_autostart` **создаёт задачу планировщика** — автозапуск не
выключается, а переходит на программу. Это правильное поведение для чекбокса
«Запускать службой» (src/main.js:1831-1834), но не для селекта «— не запускать —».

**Влияние.** Пользователь с установленной службой выбирает «— не запускать —»,
видит «автозапуск выключен», а после `refreshAll` селект снова показывает прежний
профиль, чип «включён», и при входе в Windows поднимется обход. Прямо противоположно
выбранному действию — ровно тот класс «висячих настроек», от которого переработка
должна была избавиться.

**Предлагаемая правка** (только фронт, без изменения бэкенда):

```js
} else {
  // Сначала убираем профиль автозапуска — иначе remove_service
  // оставит его и перейдёт на программный автозапуск.
  const s = collectSettings();
  s.autostart_mode = "none";
  s.autostart_profile = null;
  await invoke("set_settings", { settings: s });
  await invoke("remove_service");
  toast("ok", "автозапуск выключен");
}
```

Порядок важен: `set_settings` должна записать `mode="none"` ДО `remove_service`,
иначе `fallback` в бэкенде сработает на старом значении.

**Проверка.** Вручную (нужны права + служба): установить службу, выбрать в карточке
автозапуска «— не запускать —», перезагрузить Windows. Ожидаемый результат: обход
не поднимается, задача `ZapretGUI` в `schtasks /query` отсутствует, `state.json`
содержит `autostart_mode: "none"`.

### [Major] lib.rs:2086, 1654-1700 — повторный UAC на каждом сохранении любых настроек

**Проблема.** `set_settings` вызывает `sync_autostart` безусловно. Если прошлый
`apply_boot_task` не удался (пользователь отклонил UAC), `boot_app` остаётся `false`,
а `want` остаётся `true` — рассинхрон не «закрывается», и каждая следующая запись
настроек снова идёт в `apply_boot_task` → снова UAC.

**Влияние.** Любое изменение в настройках (DNS-провайдер, интервал обновлений —
`collectSettings` уходит на каждое изменение поля) провоцирует всплывающий запрос
прав на задачу планировщика, никак не связанный с действием пользователя. Для
не-админа это постоянный шум; после согласия — двойной UAC (известный компромисс
раздела 7 здесь не при чём, т.к. здесь UAC вообще не должен был появляться).

**Предлагаемая правка.** Запоминать неудачу согласования и ретраить только при
изменении автостарт-полей, например:

```rust
// в Settings: #[serde(default)] pub boot_sync_failed: bool
// sync_autostart: в ветке Err(e) — s.settings.boot_sync_failed = true; save()
// set_settings: вызывать sync_autostart только если поменялись
//   autostart_mode / autostart_profile / boot_app (или boot_sync_failed)
```

Минимальный альтернативный вариант: в `sync_autostart` после неудачи логировать
флаг в `AppState` и не повторять попытку до следующего явного изменения автозапуска.

**Проверка.** Юнит-тест на чистой логике решения «вызывать ли sync»
(`settings_changed_autostart_fields`), плюс вручную: отклонить UAC при выборе
профиля, затем сменить DNS-провайдера — нового запроса прав быть не должно.

### [Minor] lib.rs:1806, 1837, 2071 — блокирующее UAC-ожидание в async-командах

**Проблема.** `install_service`, `remove_service` и `set_settings` —
`#[tauri::command(async)]`, но вызывают `run_elevated_script` /
`apply_boot_task` напрямую в теле команды. `run_elevated_script`
(runner.rs:109-127) ждёт завершения повышенного процесса (`-Wait`), т.е. поток
tokio-воркера блокируется на всё время UAC (потенциально до таймаута запуска).

**Влияние.** На время UAC-диалога блокируется один воркер рантайма; остальные
`invoke` (в частности опрос `bootstrap` каждые 4 с — src/main.js:2101) могут
приостановиться. На многоядерной машине незаметно, на слабой — UI «замерзает».
`start_profile` и `apply_best_strategy` уже используют `spawn_blocking` — логично
привести к тому же.

**Предлагаемая правка.** Перенести блокирующую часть в `spawn_blocking`, как уже
сделано в `apply_best_strategy` (lib.rs:1619-1646).

**Проверка.** Вручную: запустить установку службы (появится UAC), не отвечать на
него ~30 с и убедиться, что интерфейс и опрос тулбара продолжают работать
(DevTools → Network/FPS не замирает).

### [Minor] lib.rs:812-845 — после остановки службы состояние устаревает на ~10 c

**Проблема.** `do_stop` в ветке «runtime пуст, служба запущена» вызывает
`stop_service`, но не записывает `service_running = Some(false)` и не сохраняет
состояние. `stop_all_own` (и, значит, кнопка «Остановить» в тулбаре и на плитке)
идёт именно через этот путь.

**Влияние.** До следующего тика watcher-цикла (обновление службы раз в 10 с,
lib.rs:2478-2492) `bootstrap` отдаёт `service.running = true`, а
`current_owner` — `Service(...)`: UI показывает «служба: …» и активную плитку
сразу после остановки. Самоизлечимо, но выглядит как «кнопка не сработала».

**Предлагаемая правка.** В `do_stop` после `stop_service(&data)`:

```rust
if running == Some(true) {
    let _ = stop_service(&data);
    s.service_running = Some(false);   // добавлено
    s.save();
}
```

**Проверка.** Вручную: запустить службу, нажать «Остановить» — тулбар и плитка
должны погаснуть сразу, а не через ~10 c.

### [Minor] lib.rs:638-654, 2578-2613 — инвариант автозапуска не восстанавливается на старте

**Проблема.** `migrate_removed_engine` сбрасывает `autostart_mode`/`autostart_profile`,
если профиль указывал на вырезанный движок winws2, но `boot_app` не трогает.
`provision_boot` на старте задачу **только создаёт** (`boot_app && !exists`), но
никогда не снимает. `sync_autostart` на старте не вызывается.

**Влияние.** Пользователь версии ≤1.1.0 с автозапуском через winws2-профиль после
перехода на 1.2.0 получает: профиль автозапуска сброшен, задача `ZapretGUI`
осталась, `boot_app = true`. На следующем входе в Windows GUI открывается через
`--boot`, `ack_boot` видит `mode != "profile"` (lib.rs:2224-2226) и выходит —
обход не поднимается, GUI просто висит в трее. Инвариант «задача ⇔ профиль» нарушен.

**Предлагаемая правка.** В `provision_boot` добавить снятие задачи, когда
автозапуск включён (`boot_app`), а валидного профиля нет — с тем же ограничением
«только под админом, иначе warning в журнал», что уже есть для создания:

```rust
if !state.settings.boot_app { return; }
let have_profile = /* exists valid autostart_profile */;
if !have_profile && rn::boot_task_exists() { /* попытка unregister, best-effort */ }
```

**Проверка.** Вручную: на старой версии включить автозапуск winws2-профиля (или
подготовить `state.json` с `autostart_profile` на несуществующий профиль и
`boot_app: true`), запустить 1.2.0, перезайти в систему — задача `ZapretGUI`
должна быть снята, GUI не должен открываться без обхода.

### [Minor] lib.rs:386-393 — TOCTOU в защите от повторной загрузки движка

**Проблема.** В `fetch_engine` проверка и установка `busy` разнесены:

```rust
if g.is_busy() { return Err(...); }
g.set_busy(true);
```

Между `load` и `store` два одновременных вызова проходят защиту. Комментарий
рядом прямо описывает последствия: два потока пишут в один tmp-zip, распаковка
портится.

**Влияние.** Два быстрых клика «Скачать движок» (или клик + автопроверка
`check_updates`, которая тоже идёт под `busy`) могут одновременно качать движок.
Редко, но тихо ломает установку.

**Предлагаемая правка.** Атомарная установка:

```rust
if g.busy.compare_exchange(false, true, Ordering::SeqCst, Ordering::SeqCst).is_err() {
    return Err("уже идёт загрузка или проверка обновлений — дождитесь завершения".into());
}
```

**Проверка.** Юнит-тест на `Global` (`compare_exchange` возвращает `Err` при
повторной установке) или вручную: два быстрых клика по «Скачать движок» — второй
должен получить отказ, в `data/logs` не должно быть двух одновременных загрузок.

### [Minor] lib.rs:985-992 — `start_or_switch` решает по состоянию, а не по факту

**Проблема.** Выбор ветки (repoint службы vs `do_start`) делается по
`st(g).service_running.is_none()`. Если `state.json` рассинхронизирован (служба
установлена, а записано `None` — внешний `sc create`, удалённый `state.json`,
убитый процесс), пойдёт ветка `do_start`: `stop_all_own` остановит службу фактом,
но не удалит, winws поднимется как процесс программы, а `sync_autostart` не
вызовется — два механизма автозапуска остаются несогласованными.

**Влияние.** Нарушается «механизм всегда один» в редких переходных состояниях;
watcher исправит `service_running` за 10 c, но инвариант задачи планировщика —
только при следующем `sync_autostart`.

**Предлагаемая правка.** Как и в `stop_all_own`, проверять факт:

```rust
let (installed, _) = svc::service_state();
if !installed { return do_start(app, g, id); }
```

**Проверка.** Вручную: при остановленной GUI создать службу внешней командой
`sc create zapret ...`, запустить GUI, нажать «Запустить» — должен пойти путь
пересоздания службы (в `data/logs` — `svc_install_*.ps1`, тост «Служба
переключена»), а не запуск winws как процесса программы.

### [Minor] service.rs:252-260 — «своим» считается только движок под `data/`

**Проблема.** `is_own_engine` проверяет префикс `data_dir`. Если пользователь
выбрал корень движка вне `data/` (`set_root`, src-tauri/src/lib.rs:386-403), winws
из этого корня не считается «своим»: `stop_all_own` его не останавливает, а

для работающего профиля это незаметно).

**Влияние.** Внешний/ручной winws из кастомного корня не детектится и не глушится
— жалоба «два winws конфликтуют» для этого сценария не закрывается.

**Предлагаемая правка.** Учитывать в `is_own_engine` также настроенные корни
(`roots[engine]`), либо передавать список своих корней в `own_engine_pids`.

**Проверка.** Юнит-тест `is_own_engine` для пути вне `data/`, но внутри
настроенного корня. Вручную: указать папку Flowseal вне `data/`, запустить её
`general.bat` вручную, нажать «Остановить» — процесс должен сняться.

### [Nit] runner.rs:343-354 — `pid_alive(0)` возвращает `true`

`tasklist /FI "PID eq 0"` показывает System Idle Process (PID 0), поэтому
`pid_alive(0) == true`. Сейчас pid 0 нигде не хранится: `start_or_switch` возвращает
`Runtime { pid: 0, via: "service" }`, но не сохраняет его в состояние
(раздел 7, осознанный компромисс), а фронт результат `start_profile` не использует
(src/main.js:764 — возвращаемое значение отбрасывается). Если будущий путь начнёт
сохранять такой runtime, `do_stop`/watcher будут считать процесс бессмертным.

**Предлагаемая правка.** `pid > 0 && <текущая проверка>` — одна строка, убирает
латентную ловушку.

  «задача ⇔ программный режим и валидный профиль» = `autostart_plan` + тест

## 4. Открытые вопросы к автору
